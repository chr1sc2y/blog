Rebuilding a Data Platform Under Continuous Writes

A database migration becomes a distributed-systems problem as soon as the application must keep accepting changes. A bulk copy can move records, but it cannot determine which writer is authoritative, whether a delayed event is still valid, or what happens when a successful write loses its response. Those questions define the project more precisely than the choice of destination database. Consider a multi-tenant service whose read path assembles frequently requested objects from several document collections. Background imports compete with interactive requests, and a small engineering team operates the storage stack. An application can run out of database capacity while most of its connections are idle. Every independently scaled worker brings a connection pool, every pool reserves some headroom, and a deployment temporarily runs both generations. The database sees the sum of those decisions. No individual service needs to be unusually busy for the aggregate to become expensive. Consider a shared data access service used by short-lived workers and long-running applications.
